# 移動時間模型：一次移動要幾秒

程式在 `src/kibo/motion.py`。這份文件說明它的依據與實測的吻合程度。

## 依據：控制器的原始碼

模擬器的 Docker image 直接編譯上游 `jaxa/int-ball2_simulator`（`melodic` 分支）的 `ctl_only`。
下面的檔案都在 `Int-Ball2_platform_simulator/src/platform/guidance_control/ctl_only/`。

| 事實 | 出處 |
|---|---|
| `MOVE_TO_ABSOLUTE_TARGET` 與 `MOVE_TO_RELATIVE_TARGET` 都是**先平移、平移完才轉向** | `src/pos_att_profiler.cpp` 的 `setProfile`：`seq_ = SEQUENCE::POS_ATT` |
| 平移與轉向各自是 bang-bang 剖面：量 r、上限速度 v、加速度 a；r ≤ v²/a 時 `2√(r/a)`，否則 `r/v + v/a` | 同檔 `maneuverTiming` |
| 加速度 = 有效推力 ÷ 質量；有效推力是「最吃力那顆風扇剛好到 eta × 上限」時的推力，所以**看方向** | `setProfilePos`；`src/thrust_allocator.cpp` 的 `effectiveFmax`、`allocate` |
| 絕對移動會取較短的那一邊轉（`dq.w < 0` 就取負） | `pos_att_profiler.cpp` 的 `maneuver` |
| 參數：`v_max 0.20 m/s`、`w_max 0.4363 rad/s`（25°/s）、`eta 0.4`、風扇上限 `0.06 N`、質量 `3.216 kg`、慣量 `0.0136 kg·m²`、推力配置表 `Wp`／`Wm` | `ctl.yaml` |
| action 回報成功的條件：離目標 10 cm、0.5 rad（約 28.6°）以內，**連續 3 秒** | `ctl.yaml` 的 `tolerance_pos`、`tolerance_att`、`duration_goal`；`src/ctl.cpp` 的 `reachGoal` |
| 取消或被新指令搶占時，控制器會先停下來，同樣要在容差內待滿 3 秒 | `ctl.cpp` 的 `cancelTarget` |

算出來的加速度（機體座標系）：

| 方向 | 平移 m/s² | 繞該軸轉 °/s² |
|---|---|---|
| X（機頭） | 0.0225 | 5.1 |
| Y | 0.0124 | 7.7 |
| Z | 0.0152 | 13.8 |
| (1,1,0) 斜向 | 0.0113 | |
| (1,1,1) 斜向 | 0.0091 | |

平移時機體還是**上一個點的姿態**，所以同一段位移從不同的點出發，秒數可以差到 1.5 倍；
成本矩陣因此不對稱，路線規劃（Held-Karp）照樣處理。

## 幾個數字感

| 移動 | 秒 |
|---|---|
| 沿機體 X 軸 0.3 m | 7.3 |
| 沿機體 X 軸 1 m | 13.3 |
| 沿機體 Y 軸 1 m | 18.0 |
| 沿機體 X 軸 4 m | 28.9 |
| 繞 Z 轉 90° | 5.4 |
| 繞 X 轉 90° | 8.4 |

短腿很貴：0.3 m 也要 7 秒，再加轉向。舊模型（距離 ÷ 0.1 m/s 加 角度 ÷ 15°/s）會低估短腿、高估長腿。

差的平均 −0.95 秒，標準差 2.05 秒。

- 轉角大於 28.6° 的 11 段：差在 ±1 秒內（一段 +2.7 是起跑第一段）。
- 轉角小於 28.6° 的 3 段預測偏多 3 到 6 秒：姿態一開始就在 0.5 rad 的容差內，action 不等轉向就回報成功，
  機器人其實還在轉。我們的程式回來後會自判，等姿態真的到位才送通知，所以這幾秒大部分還是會花掉。
- 「3 秒駐留」幾乎不花額外時間：進 10 cm 容差比剖面結束早大約 3 秒，兩者抵銷。所以模型的 `overhead_sec` 取 0。

到點精度：位置誤差約 1 cm，對中與滾轉 1° 左右（一次 4.5° 與 8.2°）。兩場共 15 點自判都是 Lv3，官方 `result.json` 也都是 3。

### 各難度能去幾個點

用模型對 300 個隨機場景規劃（每點穩定 1 秒），不同的保險秒數（`BudgetConfig.margin_sec`）：

| 保險 | hard（10 點）平均 | veryhard（12 點）平均 |
|---|---|---|
| 15 s（目前） | 8.86 | 9.10 |
| 10 s | 8.98 | 9.34 |
| 8 s | 9.03 | 9.44 |
| 5 s | 9.08 | 9.62 |

easy（6 點）與 normal（8 點）在 300 秒內全部去得完（平均約 211 與 261 秒）。
保險從 15 秒降到 10 秒，veryhard 平均多 0.24 點；代價是對「比模型慢」的容忍變小。
本機五場的整場誤差都在 −8 到 +0.5 秒之間，但 Web 模擬器有擾動（本機沒有），逾時的代價也還不知道，
所以先維持 15 秒。

### 試過但沒採用

- **先原地轉到目標姿態、再平移**（讓平移時機體朝向比較有利）：多一次 action 的等待，整條路線只省約 1%。
- **不等 action 回來就送下一個指令**：控制器被搶占時會先停穩 3 秒，沒有好處。
- **目標點在 Lv3 容差內往來向偏幾公分**：每段腿約省 1 秒，但會吃掉對擾動的餘裕；等看到 Web 模擬器的擾動再說。

### 尾段自判

action 回來之前機器人通常已經在 Lv3 內停了 1.5 秒左右。節點把導航（約 200 Hz）降到 20 Hz 留最近 3 秒，
action 一回來先看這段紀錄：最近 1 秒每一筆都達標就直接回報，否則照舊等 1 秒。每點省約 1 秒。
紀錄裡有一筆沒達標（例如滾轉還在擺）就不用它；第八場的 #7 就是這樣，多等了 4.5 秒才回報，仍是 Lv3。

## 還沒驗證

- Web 模擬器與實機的參數可能不同（`ctl.yaml` 的註解留著另一組較嚴的容差）。任務中的速度校正會把整體偏慢的情況等比例修掉，最多 2 倍。
- 規則書附錄 #22 的 Microgravity module（擾動）在本機預設關閉（`ENABLE_GRAVITY_MODULE=false`）。
