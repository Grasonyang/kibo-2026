# Spec：第 7 屆 Kibo-RPC 資格賽解法

狀態：draft，2026-11-04；同日依 reviewer（Standards、Spec 兩軸）的審查更新為實作現況。由 Claude 在使用者不在場時以 `to-spec` 格式整理；seam 由 Claude 代為決定，列在「測試決策」，使用者回來後可以推翻。

## 問題

我們要交一支程式給 JAXA 的 Web 模擬器，它控制 Int-Ball2（IB2）在 5 分鐘內拜訪 6 到 12 個位置隨機的 CheckPoint、在每一點把相機對準 AR marker 並維持 1 秒，最後到 GoalPoint 回報。程式會被自動跑 10 次取平均，所以要的是**穩定**，不是偶爾的高分。看程式的人可能完全沒有機器人與 ROS 背景，所以程式與文件都要從零講起。

目前手上沒有官方模擬器（要用隊伍帳號從 jaxa.krpc.jp 下載），所以本 spec 的範圍是「不需要模擬器就能完成、且拿到模擬器後能直接接上的部分」。

## 解法

把程式拆成兩層：

1. **任務邏輯層（`kibo`）**：純 Python，不碰 ROS。負責「讀 CheckPoint、排路線、算每一點該站在哪、朝哪看、什麼時候該放棄、什麼時候回報」。本機就能用 pytest 測，而且可以用一個**假機器人**把整場任務跑完、算出估計分數。
2. **ROS 接線層（`krpc_user`）**：把 ROS 的 topic、service、action 接到任務邏輯層。這層很薄，只做翻譯，邏輯都不放這裡。拿到模擬器才能測。

兩層之間只有一個介面：`Robot`（移動到某個姿態、讀目前姿態、回報通過、回報完成、讀剩餘時間）。

## 使用者故事

1. 身為參賽者，我要程式能從 `/mission/get_checkpoints` 的 JSON 得到每個 CheckPoint 的位置、三層距離餘裕、目標姿態、對中與滾轉餘裕，才能據此行動。
2. 身為參賽者，我要程式自己決定拜訪順序，讓總路程最短，並以 GoalPoint 收尾，才能留下最多剩餘時間（倍率最高 2 倍）。
3. 身為參賽者，我要每一點的目標姿態確實讓相機指向 marker、滾轉符合要求，才拿得到 Lv3。
4. 身為參賽者，我要程式在到達後先確認「位置、對中、滾轉」三項都在 Lv3 餘裕內並已穩定，才送 `checkpoint_passed`，避免送早了被判失敗。
5. 身為參賽者，我要程式隨時知道剩餘時間，當剩下的點來不及時主動放棄價值最低的點、保住 Goal，因為 Goal 與倍率乘在全部分數上。
6. 身為參賽者，我要任何一次移動失敗或逾時都有上限次數的重試，之後跳過該點，程式絕不卡死。
7. 身為參賽者，我要程式在收到 `/ib2_user/stop` 時取消所有動作後才回應，符合 JAXA 的安全審查。
8. 身為參賽者，我要在沒有模擬器的電腦上也能把整場任務「跑一遍」看估計分數，才能快速比較不同策略。
9. 身為零基礎的讀者，我要有一份從「這個比賽在玩什麼」講起的文件，加上圖，才能看懂程式在做什麼。
10. 身為零基礎的讀者，我要每個模組開頭有白話說明「輸入、輸出、為什麼存在」。
11. 身為參賽者，我要 log 記下計畫、每一步的目標與結果、剩餘時間，才能在 Web 模擬器的 log 裡看出哪裡出錯。
12. 身為參賽者，我要程式的每個迴圈都有次數與時間上限，才通得過決賽的原始碼審查。
13. 身為參賽者，我要所有程式都能在 Python 3.6 執行。
14. 身為參賽者，我要拿到模擬器後，只需要把接線層貼進官方範本就能跑。
15. 身為參賽者，我要文件列出幾個還沒做、但可能加分的點子，以及各自的代價。

## 實作決策

- **座標與姿態**：位置用 `(x, y, z)` 公尺，姿態用四元數 `(x, y, z, w)`，與規則書和 ROS 一致。相機視線是機體 +X。自己實作四元數運算（旋轉向量、共軛、相乘、兩向量夾角），不依賴 `tf` 或 `scipy`，因為 3.6 映像裡不一定有。
- **CheckPoint 資料**：`get_checkpoints` 的 JSON 解析成具名結構；bands 依 level 由嚴到寬排序；`goalpoint_id` 指向其中一個 CheckPoint，當作終點。
- **路線**：Held-Karp 動態規劃（中途點 ≤ 11，狀態 2^11 × 11，本機 0.1 秒內；成本先算成矩陣），從起點出發、經過所有非 Goal 點、以 Goal 結束。中途點超過 11 個改最近鄰，不會爆。成本先用直線距離加上轉向角的時間換算；之後若模擬器顯示速度模型不同，只需要改成本函式。
- **目標姿態**：優先用伺服器給的 `attitude.quaternion`，但用自己的幾何檢查它是否真的對準 marker；若對中角超過最嚴的餘裕，改用「相機指向 marker、滾轉盡量貼近給定姿態」的姿態（從機體位置算 `look_at`，相機在視線上所以同樣對中）。這是對伺服器資料的保險，手冊範例是 0.0°，正常不會觸發。
- **到點判定（本機）**：照官方 `judge.py` 的算式，以 nav 的實際姿態算三項指標與對應的 Lv（[simulator-internals.md](../kibo/simulator-internals.md)）。連續 5 筆新的導航資料（間隔 0.25 秒，涵蓋規則要求的 1 秒）都達標才算**穩定**；移動的 action 回來時，若最近 1 秒的導航紀錄每筆都達標，直接算穩定。目標 Lv 預設 3；這一點的**餘裕**（剩餘時間扣掉後面路線還要的秒數）少於 5 秒才降到 1。有餘裕時前 3 秒用較嚴的標準：三項都要在 Lv3 上限的八成以內（Goal 點的滾轉讀數會放大誤差）。穩定就回報。沒穩定（逾時 6 秒）時用**最後一次**判定：餘裕超過 15 秒就再移動一次（只一次）再穩定；最後一次判定至少 Lv1 **且這一點有成功移動到**才回報（每個點官方只判第一次通知，不回報一定 0 分；手冊 6.5 說移動失敗不送到達通知），並在紀錄標 unstable；整段期間都沒有導航資料就不回報，因為不知道自己在哪。
- **時間預算**：`TIME_LIMIT_SEC = 300`，保留固定安全餘裕（預設 15 秒）給 Goal 與回報。每個 leg 的估計時間用照控制器原始碼的移動時間模型（先平移再轉向、bang-bang、加速度依機體方向，[motion-model.md](../kibo/motion-model.md)），每點另加 1 秒穩定時間。來不及時精確地挑「時間內能去最多點」的一組（各點分數相同），一樣多選最快的；Goal 永不刪。**還不知道**：漏了點之後 Goal 分數還給不給（規則書附錄 #20 字面是「passes all CheckPoints」，模擬器 cheat sheet 的欄位叫 `all_checkpoints_bonus`），分數在伺服器端算，要問主辦。
- **時間起點**：t0 取 `/ib2_user/start` 到來的時刻。規則書說計時從 Release 完成起算；若 start 比 Release 晚，剩餘時間會被高估，待模擬器用結果 JSON 的 `duration_sec` 校正；校正前不把 `margin_sec` 往下調。
- **不死保底（council R1）**：清單解析能救就救（單點壞跳過、count 不符以實際為準、Goal 不在清單用最後一點、缺 attitude 自己算）；超過 11 個中途點改最近鄰；任何例外都走到 `mission_finish`。
- **速度線上校正（council R2）**：只用 ≥ 0.5 m 的腿、累積 20 秒模型時間後，比較模型預測秒數與實際秒數的累積比，慢超過 11% 就把規劃用的秒數同比例放大（原本是 25%，慢 20% 到 24% 落在死區裡把保險吃光，issue #16），上限 2 倍；比例回到死區內就拉回預設（不留棘輪），但永遠不比預設快。重試的腿與修正用的再移動不算，因為起點不可信。`move_timeout` 取 60 s 與估計腿三倍的較大者。
- **時間安全（issue #16）**：兩層。**硬上限**保證完成回報準時：到點後的等待最晚等到時限前 3 秒（`finish_reserve_sec`，之後還要回報這一點與送完成回報）；移動的逾時再早 5 秒（`cancel_reserve_sec`，逾時後取消 action 最多等這麼久），來不及就不送（含重試），最壞時放棄 Goal 也要準時完成。等待另外不超過這一點的餘裕；沒有移動成功的點不回報，所以只讀一筆不等。**回饋**讓規劃早一點刪點：每點實際停留的秒數（到點到回報完）取最近三點的中位數，比設定的 1 秒大就用它當之後每點的停留時間（中位數而不是平均：單獨一點特別久不該讓之後每點都多留）。通知也受限（issue #17）：一次通知最多等 15 秒（`notify_timeout_sec`），而且要在時限前 1 秒回來（`finish_call_sec`，留給完成回報的服務呼叫）；時間不夠就不送，重試前的暫停也算在裡面。ROS 端等 action server 出現的時間算在同一個上限裡，通知逾時後送出取消但不等它的回應。快到時限時不做 marker 的記錄。已知沒蓋到的：完成回報的服務呼叫本身卡住（ROS 端等服務出現 10 秒、等回應 10 秒）；那是最後一步，卡住時沒有別的事可以做。另外，這些上限都用模擬時鐘計時，時鐘停住時 actionlib 的等待不會逾時（剩餘時間也不會減少，所以邏輯一致）。
- **探針旗標（council R4）**：`notify_even_if_level0`、`skip_one_waypoint`、`deliberate_late_after` 預設關，只在資格賽模擬器上定規則世界用。settle 只計 stamp 變新的導航樣本；沒有成功移動不回報（手冊 6.5）。
- **任務狀態機**：`PLAN → MOVE → SETTLE →（REFINE）→ NOTIFY →（下一點）→ GOAL → FINISH`，失敗分支有重試上限：移動每點最多嘗試 2 次（`MOVE_INVALID` 不重試）、回報最多 2 次、取清單最多 3 次。狀態機不呼叫 ROS，只呼叫 `Robot` 介面。
- **`Robot` 介面**（抽象類別）：八個必要方法 `now`、`pose`（沒資料回 None）、`move_to(pose, timeout) -> 字串常數 MOVE_SUCCESS/TIMEOUT/ABORTED/INVALID`、`sleep`、`mission_start`、`get_checkpoints_message`、`notify_checkpoint(id, timeout)`、`mission_finish`，加兩個選用 `stop_requested`、`log`。ROS 版與假機器人版各實作一次。ROS 版的服務呼叫放在 daemon thread 裡用 Event 等，因為 `ServiceProxy` 本身沒有逾時。
- **假機器人**：等速直線加等角速度轉動的簡化模型，可注入位置雜訊與偶發失敗，並依 bands 判 Lv 算分，讓策略比較有數字可看。它不是物理模擬，分數只能做相對比較。
- **ROS 接線層**：照官方範本結構（`/ib2_user/start`、`/ib2_user/stop`、`/ib2_user/ready` 保留），`Robot` 的每個方法對應一個 action 或 service，全部有逾時與取消。
- **影像（只記錄）**：主流程靠導航資料，官方評分也是用導航的姿態。每到一點，若 `Robot.marker_in_body` 回得出該 marker 在機體座標系的位置，就記一行它與導航預期位置的差（`MissionConfig.log_marker`），不拿來移動。「用相機修正幾公分」的路徑還在（`camera_fix_max_m`，預設 0 = 關）：本機模擬器裡相機換算的深度與導航差約 15 cm，而導航誤差只有 1 cm，開了只會變差。
- **Log**：每個階段一行，開頭固定是剩餘秒數，後面是階段與數字（路線與估時、移動結果、三項指標與 Lv、是否穩定、回報結果）。

## 測試決策

好的測試只透過公開介面看行為，不碰內部。seam：

| Seam | 抓得到 | 抓不到 |
|---|---|---|
| `parse_checkpoints(json_str)` | JSON 格式理解錯誤、bands 排序 | 伺服器之後改格式 |
| `plan_route(start, checkpoints, goal_id)` | 順序錯、沒以 Goal 收尾、漏點 | 成本模型不符真實速度 |
| 幾何：`look_at`、`angle_between`、`roll_error` | 姿態算錯、對中與滾轉指標錯 | 伺服器判定與我們公式的細微差異 |
| `judge(pose, checkpoint)` | Lv 算錯、邊界 | 伺服器實際的判定頻率 |
| `run_mission(robot, clock)` 搭配假機器人 | 流程卡死、重試無上限、時間預算失效、Goal 被刪、相機修正是否被採用或拒絕 | 真實動力學、ROS 行為 |
| `observe_markers(gray, K, D)` 搭配合成影像 | 偵測與位姿的座標慣例、鏡像 | 真實鏡頭的畸變與曝光 |

測試用已知答案的數字（例如手算的距離、規則書的 marker 位置），不用程式自己的算法回推。ROS 接線層沒有本機測試，第一次在模擬器跑就是它的測試。

## 其他

- 分數常數（各 Lv 的點數、倍率曲線）規則書沒給。假機器人用可調的假設值：Lv3=10、Lv2=6、Lv1=3、Goal=20、倍率依剩餘時間線性從 1 到 2。拿到模擬器後用結果 JSON 校正。
