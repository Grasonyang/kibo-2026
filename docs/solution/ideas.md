# 點子與取捨

已做的在上面，還沒做的在下面，每一條都寫「為什麼值得」與「代價」。拿到模擬器後，用
`python -m kibo.simulate` 與 Web 模擬器的結果 JSON 來決定哪些真的要做。

## 已經做進去的

| 點子 | 為什麼 | 代價 |
|---|---|---|
| **先保 Goal，再搶點**：時間不夠就刪「省最多秒」的點，Goal 永不刪 | Goal 分數與剩餘時間倍率是乘在全部分數上的；沒到 Goal 就沒有 Goal 分，而且（推測）完成回報也來不及、倍率最低 | **前提未驗證**：規則書附錄 #20 的 Goal 分數字面上要求「通過所有 CheckPoint」，若真如此，刪點會連 Goal 分一起丟，策略要改成不刪；偶爾也會太保守 |
| **最佳順序用精確解**（Held-Karp），不用最近鄰 | 12 點以內精確解只要幾十毫秒，沒理由用近似 | 超過 16 點會爆；規則上限 12，沒問題 |
| **轉向也算成本** | IB2 每點都要轉到指定滾轉，大轉彎很花時間 | 角速度是猜的 |
| **自我判定再回報** | `checkpoint_passed` 送早了會被判失敗，而且沒有無限次機會 | 每點多花幾秒穩定 |
| **沒有模擬器也能整場跑** | 策略與流程的 bug 在本機就能抓，不用每次等 Web 模擬器排隊 | 假機器人不是物理，分數只能相對比較 |
| **時間不夠時放寬到 Lv1** | 快沒時間時，Lv1 的分數好過 0 分 | 門檻 40 秒是猜的 |
| **速度線上校正**（council R2）：長腿的實際秒數比模型慢 25% 以上，就把速度同比例調慢 | 速度是第一敏感參數：猜錯一半時 Goal 率從 10/20 變 20/20（8 點；12 點是 14/20 → 19/20） | 只往慢修；起停時間與轉向的混淆已排除，但真機器人的門檻可能要調 |
| **不死保底**（council R1）：清單壞、例外、點太多都降級，任務開始就一定完成回報 | 整場 0 分的路徑比任何調參都貴 | 無 |
| **探針旗標**（council R4）：漏一點、故意逾時、自判 0 也回報 | 兩場就能定規則世界 | 決賽程式不得開啟 |

## 值得試的

### 1. 到點後用相機做微調——已做，ROS 端未測，效益 fake-sensitive
導航（`/sensor_fusion/navigation`）的位置可能有漂移；相機看 marker 的位姿是「相對 marker」的，
正是伺服器判定用的基準。到點後用 ArUco 算出相機到 marker 的向量，和目標比對，
用 `MOVE_TO_RELATIVE_TARGET` 修正幾公分。

已完成：`src/kibo/vision.py`（偵測、`solvePnP` 位姿、相機到機體座標換算、預期位置、修正量），
同時支援 OpenCV 3.x 與 4.7+ 的 ArUco API，用合成影像測到 5 mm 內（`tests/test_vision.py`）。
已接線：`Robot` 多了兩個選用方法 `marker_in_body`、`move_relative`；`mission.visit` 在 settle 不穩定時先試相機修正
（2026-11-10 上機後：相機修正預設關，每點只記一行相機與導航的比對；原因見 `docs/kibo/simulator-internals.md` 的 E6。）
（修正量 ≤ 0.3 m 才信），不行才再絕對移動一次。假機器人有假相機，`--camera` 可開；ROS 端訂閱 `/camera_main/*`，
不用 cv_bridge，直接 numpy 轉灰階。
代價：影像延遲、要先確認伺服器判定到底用哪個座標、字典是不是 `DICT_4X4_50`、ROS 端未測。

### 2. 用 `/ctl/status` 判斷移動結束，而不是只等 action result
手冊 6.3.2 說可以看狀態從 `MOVE_TO_*` 變成 `KEEP_POSE`。若 action result 比實際停穩晚，
用狀態可以省幾秒；若更早，就能避免在還在飄的時候取樣。
代價：多一個訂閱與一些狀態判斷。

### 3. 順路的點「邊飛邊看」
現在是「停、穩定、判定」。如果兩個 CheckPoint 很近（例如 marker 1 與 7 都在 SAIBO 架上，
只差 0.3 m），可以規劃一條連續的小路徑。
代價：要能連續送目標或改用 `/ctl/wrench`，複雜很多；先量化到底省多少秒再說。

### 4. 離線跑很多次，挑出「最差情況」的參數——工具已做，結論要跨世界看
`python -m kibo.tune` 對四個規則世界（Goal 需不需要全點 × 逾時保不保留分）各算平均，
再算「最大後悔」。只有名次跨世界不變的結論才算數；目前站得住的只有「速度校正」與「刪點保 Goal」，
其餘（只求 Lv2、保險秒數、相機）都標 fake-sensitive，見 README 第 5 節。
代價：假機器人要先用模擬器資料校正，否則調的是假參數。

### 5. 兩個 marker 共用一次定位
marker 1（SAIBO，z 0.681）與 7（MELFI1，z 0.372）在同一面牆、x 相同。到其中一點後
往上或往下平移 0.3 m 就到另一點，不用重新規劃。路線規劃只看座標，通常會把這種近點排在一起，
這條是把兩段移動合併成相對移動。
代價：小。

### 6. 時間倍率的形狀
倍率曲線沒公布。如果是階梯狀（例如剩 60 秒以上才 2 倍），策略會變成「拼速度」；
如果是線性，多拿一個 Lv3 通常比省 10 秒划算。拿到結果 JSON 後，拿幾場不同完成時間的
`Time Bonus` 反推。
代價：只是分析。

### 7. 把 `judge` 的視差假設做成開關——已做
（已解決：官方 `judge.py` 的對中從機體中心量，`camera_offset_m` 這個開關已移除。）

## 不打算做的

| 點子 | 原因 |
|---|---|
| `/ctl/wrench` 直接施力 | 手冊明說難度高、與 `/ctl/command` 混用會有未預期狀態；資格賽的瓶頸不在這 |
| 用機器學習辨識 marker | ArUco 本來就是為這個設計的，OpenCV 內建 |
| C++ 重寫 | 沒有效能瓶頸；見 ADR-0001 |
