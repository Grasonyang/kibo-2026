# 回顧（2026-11-10 至 11-11，模擬器接線階段）

範圍：取得官方模擬器、上機、兩個 PR（#3 上機、#12 整理）、兩個環境 PR（#9 CI、#11 本機驗證）。約 25 場模擬。

## 做對的

- **先讀官方原始碼，再跑模擬器**。評分模組、場景產生器、控制器的原始碼回答了大半「要上機探針或問主辦」的問題，時間模型也是照控制器的公式寫的，不是擬合。
- **用官方函式產生黃金值**。把 `judge.py` 的數學函式原封不動抽出來執行，結果寫成測試的期望值；之後每次改判定都有獨立的對照。
- **每修一個問題，先讓它在本機紅一次**。影像 callback 沒定義 → pyright 納入 `ros/`；起跑保護誤判 → 連線清單的判讀抽成純函式加測試；Goal 過早回報 → 用「還在轉的假機器人」重現。
- **兩軸 reviewer 用全新 context**。兩次審查都抓到作者看不到的東西：第一次是起跑保護的查詢沒有逾時；第二次是 reviewer 自己用 6000 組隨機輸入比對重構前後，找到「等到逾時、掉一級」的反例。

## 踩到的

- **節點自己的 log 說任務完成，官方卻沒有成績**（兩次）。只看自己的 log 會以為一切正常。
- **修掉一個延遲，露出它原本掩蓋的競賽**。DNS 的 5 秒延遲剛好擋住起跑競賽；修掉延遲的下一場就中了。
- **背景連跑模擬時改了程式**。`sim.sh run` 每場啟動時才同步，差點讓回歸跑在改到一半的程式上；後來改成取消排隊、改完再重跑。
- **重構夾帶規則變更**。把「頭尾滿 1 秒」順手套到即時取樣上，自以為只是多等 0.25 秒。
- **`ruff check --fix` 會刪掉為了重新匯出而 import 的名字**，然後別的模組 import 失敗。這次發生兩回。
- **手工造的測試資料落在公式的奇異點**。共用的 Goal 測試點剛好正對 −X、姿態整整 180°，官方的滾轉讀數在那裡退化成 0，滾 15° 也判 Lv3。
- **量錯導航頻率**。節點啟動時模擬時鐘還是 0，用「啟動到現在」當分母，200 Hz 量成 13 Hz，尾段紀錄因此留得太短。

## 建議改環境（依嚴重度）

1. **沒有會自動跑的防線**。CI 已寫好（#9），但 GitHub 帳號有帳單問題，工作沒有啟動；要帳號擁有者處理。在那之前有 `scripts/check.sh`（#11），hook 要自己裝。
2. **看不出一場模擬跑的是哪一版程式**。建議 `sim.sh run` 同步時寫下 commit 與是否有未提交的改動，節點啟動時印出來，`sim_report.py` 顯示（#14）。
3. **「以官方結果為準」寫進 dev-env**（本 PR 已加），連同另外三條跑模擬器的注意事項。
4. **AGENTS.md 加一行指到兩份實測文件**（本 PR 已加）。這一輪花了不少時間重新推導「官方到底怎麼判」，之後的 agent 應該直接讀到。
5. **reviewer 的 brief 值得固定成範本**（上一次回顧的第 2 條，這次再次有效）：範圍、軸、專案約束、要特別找的東西、輸出格式；重構的審查再加一條「比對新舊版在哪些輸入下結果不同」（#14）。
6. **重構的 ticket 寫「行為不變」時，附上怎麼驗證**：指定比對新舊版的方法（隨機輸入或既有測試不改斷言），不要只靠作者自己判斷。併入上一條的範本。
